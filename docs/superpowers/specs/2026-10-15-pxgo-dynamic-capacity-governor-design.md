# PxGo dynamic runtime capacity governor — architecture specification
Date: 2026-10-15
Design status: KitAuditor round 3 PASS (0 blocking, 0 warning, 0 suggestion); no implementation authorization
Scope: PxGo runtime admission and resource-pressure handling; not a process scheduler

## 1. Decision and objectives
PxGo defaults to **AUTO/DYNAMIC** capacity. Ordinary users never choose Go worker, thread, or goroutine counts. Go's runtime owns goroutine scheduling, GOMAXPROCS, netpoll and OS threads; the OS owns socket scheduling and process resource limits. PxGo owns **admission of new work**, resource-pressure observation and overload/recovery. Process Guardian owns process viability/restart **only for genuinely fatal/unrecoverable failures**. Resource saturation is never a reason to restart a healthy process.

Goals: zero-tuning UX; safe bursts; sustained HTTP and long-lived tunnels; bounded resource growth; explicit failure/recovery; compatibility; observable decisions; portable Linux/Windows baseline. Non-goals: an event-loop rewrite, goroutine pool, custom OS-thread scheduler, predictive ML, universal optimum, rewriting HTTP transport/auth, or latency-targeting CONNECT/SSE/WebSocket sessions.

## 2. Current state: verified source anchors
- `internal/config/config.go`: Defaults workers=1, threads=32; Config.Workers/Threads and source provenance exist. `pxgo.ini` [settings] exposes both as compatibility values. No max-connections key currently exists.
- `internal/proxy/proxy.go`: validateServerBudgets requires positive workers and threads, checks product overflow; connectionBudget=workers*threads. Start() creates a **single shared** buffered admissionSlots channel of that capacity across listeners; `http.Server` sets ReadHeaderTimeout/ReadTimeout/WriteTimeout/IdleTimeout and ConnState clears client auth state on Closed/Hijacked.
- `internal/proxy/admission.go`: Accept() calls underlying Listener.Accept() **before** blocking on sending to slots; the accepted socket can sit waiting for a slot, with no per-wait timeout. Close() unblocks this wait. admissionConn.Close() releases once. This is a capacity gate, not a worker/thread pool.
- `internal/proxy/connect.go`: CONNECT dials upstream **before** Hijack, reserves tunnel shutdown ownership, forwards buffered upstream/client bytes, then starts one goroutine for relay. `internal/proxy/relay.go` launches two copy-direction goroutines and waits; half-close and idle behavior are important. `internal/proxy/tunnel.go` maintains pending/tunnel registry and active atomic counter, and drains on shutdown. Hijacked connections still hold downstream admission ownership until closed.
- `internal/proxy/transport.go`: bounded transport cache (64); ordinary http.Transport uses MaxIdleConns=100 and MaxIdleConnsPerHost=32; authenticated connection-bound transport clones set MaxConnsPerHost=1 and MaxIdleConnsPerHost=1. `transport_cache.go` owns eviction/closing. These are distinct from downstream admission and must not be globally overwritten.
- `internal/proxy/supervisor_runtime.go` and `internal/supervisor/supervisor.go`: existing runtime recovery handles route/auth/network outcomes and fatal classification. Extend observability/coordination rather than add a competing supervisor. Process Guardian remains a separate fatal-process boundary.
- `internal/diagnostic/snapshot.go` and `internal/proxy/diagnostic.go`: Doctor already reports Process CPU seconds/RSS/goroutines, Runtime health/fatal, ActiveTunnels, redacted config sources and events. Extend the same snapshot.
- `nofile.go`, `nofile_unix.go`: Unix startup attempts to raise RLIMIT_NOFILE toward 65536 with fallbacks and warning below 1024. **65536 is a requested OS limit, not an admissible connection target**; each CONNECT typically consumes at least downstream + upstream descriptors, plus DNS, transport, files and headroom. Windows handles require native handling, not Unix RLIMIT assumptions.
- `docs/benchmarking.md`: existing reproducible bench-e2e, HTTP 1 KiB/10 MiB, CONNECT, SSE, soak, client counts 1/10/50/200, immutable-style raw evidence and Windows domain auth external-driver gate. Extend rather than replace.

## 3. Ownership and minimal architecture
```text
net.Listener -> bounded cancellable admission wait -> http.Server
                    |                   |
                    v                   +-> existing CONNECT/tunnel/transport/auth
           capacity governor (one owner per Server)
                    ^
                    |
   owned counters + sampled Go/OS signals
                    |
     existing Doctor/events/runtime supervisor
```
Use one server-scoped governor, not one per listener, transport, destination, auth identity or worker. No new background scheduler; a lightweight periodic sampler/controller (or existing maintenance-loop cadence if adequate) and atomic counters are sufficient. Keep all existing transport/auth/tunnel ownership. No per-connection timer/goroutine solely for capacity control.

**V1 admission choice: preserve current Accept-then-wait backpressure, but make the shared gate dynamic, bounded and cancellable.** Each existing http.Server.Serve loop calls its wrapped listener Accept serially: at most **one accepted-but-waiting socket per listener** (provided no additional accept loop is introduced). After raw Accept, acquire the shared governor permit immediately if available; otherwise wait up to one finite, benchmark-calibrated admission-wait deadline, or until a permit becomes available, listener/server shutdown, or emergency gate cancellation. On timeout close that one socket and return a **temporary** accept error whose retry behavior must be verified against net/http.Server.Serve; do not accidentally cause Serve to exit, spin or restart. The next Accept cannot happen until this wait finishes, leaving further clients in the OS backlog rather than rapidly draining and closing them. One waiting socket/FD per listener is a bounded resource cost; account for it in envelope headroom. Never claim raw TCP close is HTTP 503. An already admitted keep-alive connection retains ownership until Close; no per-request capacity limit.

**Multi-listener fairness:** one shared FIFO-style waiter notification/permit arbitration across listeners, no listener-local capacity quota; wake waiting listeners on release, window increase and shutdown. No starvation guarantee from Go select alone: implement a minimal fair waiter ordering only if contention tests demonstrate starvation; otherwise shared wake/recheck with bounded waits is enough. A waiting listener never reserves a slot before it accepts. A timed-out waiter releases its accepted socket and wait registration exactly once. Close must interrupt both underlying Accept and permit wait; shrinking the window must wake/recheck waiters, not steal permits or close existing clients. Transient raw Accept errors retain net/http's existing temporary-error backoff behavior; admission wait timeout must use an explicitly recognized temporary error or a controlled retry mechanism with bounded backoff, and must not silently terminate Serve. Permanent listener errors follow existing shutdown/error propagation. Test burst retry amplification, backlog pressure, listener fairness, timeout CPU, shutdown races and recovery, including capacity becoming available while net/http.Serve is in an existing temporary-Accept-error retry-backoff interval. If measured retry delay or churn is unacceptable, use gate-controlled pause before subsequent Accept calls, without introducing a separate accept scheduler.

## 4. Hard envelope versus soft window
`max-connections` is a **manual HARD CEILING on concurrently admitted downstream TCP connections**, not a desired concurrency, throughput target, upstream pool size, or goroutine count. A positive operator value applies an upper bound; disabled/unset/0 means AUTO with no user-imposed connection ceiling. The governor still applies its own derived safety envelope and dynamic soft admission window in either case:
`effective_admission_limit = min(dynamic_soft_window, resource_safety_envelope, positive_manual_ceiling_if_any)`.
Counts include idle downstream keep-alive, in-flight HTTP and hijacked tunnels until actual downstream close. A tunnel also consumes upstream resources; budget resource headroom accordingly. V1 does not require exact upstream socket accounting: downstream ownership and existing active-tunnel count are authoritative. A single pending-CONNECT-establishment counter at the existing handler boundary is optional if measured bursts justify it; exact upstream-open and pending-dial instrumentation is deferred. A downstream slot is acquired once and released once; shutdown/hijack must not leak or double-release.

**Deterministic envelope contract.** Capability-detect once at startup and record per-sensor supported/unsupported, then track fresh/stale/invalid. Linux: where cheaply available, use RLIMIT_NOFILE plus actual process FD usage to derive remaining descriptor headroom; the raised nofile target is not usage. Windows: use supported native process handle information as a **pressure indicator**, not an FD-equivalent socket count unless validated against real socket capacity; no invented RLIMIT translation. Process RSS with a verified applicable process/container/job memory limit may yield enforceable headroom; RSS without a reliable limit is advisory only. Runtime heap/GC/scheduler and CPU are advisory. Existing downstream active count is enforceable; active tunnels are supporting evidence, not additional downstream slots. Per-connection FD cost and reserved OS/service headroom must be conservatively calibrated by platform workload (especially CONNECT); never divide by a zero/unknown cost.

At startup, **before sensors become fresh**, enforce a finite, platform-tested fallback hard envelope F and initial soft window W0 <= F; neither is an expected concurrency target. For each sampling epoch: compute valid enforceable candidate limits only from **fresh, consistent, supported, calibrated** measurements; choose hard_envelope = min(F, all valid enforceable candidates), except an explicit emergency override closes new admission. This makes F a finite safety guardrail, not a new 32/512 performance cap; F and W0 are release-calibrated, not specified numerically here. Unknown/stale/contradictory samples contribute **no positive headroom**: retain the last known safe lower envelope (never expand based on missing data), bounded by F; if no previous valid sample, use F and inhibit growth until healthy independent pressure evidence is available. Contradictory data is flagged invalid and never averaged into a false positive. Lower envelope immediately restricts *new* admissions without killing active connections. Restoring a higher envelope requires consecutive fresh healthy samples and cooldown. Emergency EMFILE/ENFILE, verified critical memory exhaustion or verified critical handle pressure overrides all candidates and sets **new-admission allowance to zero** with cooldown/probe recovery, while existing connections and process remain alive. If no reliable sensor can establish a safety envelope for a platform, that platform must not graduate from shadow/opt-in to default AUTO until fallback calibration passes; do not guess numeric thresholds.

## 5. Controller: pressure-aware AIMD with hysteresis
**Separate demand from pressure.** Demand signals: downstream utilization near the soft window, queued/waiting admission, timeouts and rejected attempts. These permit **growth consideration only**, never shrink. Independently verified pressure: fresh, calibrated FD/memory headroom breaches or verified hard OS resource errors; advisory Go/OS signals may corroborate but cannot alone force shrink. CPU%, raw goroutine count, wait latency, retry volume and upstream auth serialization are **not pressure truth**. V1 mandatory owned counters are active downstream plus existing active tunnels; one pending CONNECT-establishment counter may be added only if measurements justify it. Do not wrap http.Transport or auth/retry paths for exact upstream-open/pending-dial counts. Sample cheap native signals at bounded cadence; never per request/connection.

**Deterministic three-state transition contract** (all dwell, step and threshold parameters benchmark-calibrated, no invented values):

| Current state | Guard evaluated per sample | Next state and window action |
| --- | --- | --- |
| normal | Verified independent pressure persists for entry hysteresis, or emergency | pressure; multiplicative shrink once per bounded pressure epoch; emergency overrides admission immediately |
| normal | No pressure; sustained demand near window; fresh healthy pressure evidence; growth cooldown elapsed | normal; additive growth capped by envelope/manual ceiling |
| normal | No demand, missing/stale pressure evidence, or cooldown active | normal; hold, **never shrink from saturation alone** |
| pressure | Pressure persists | pressure; hold or further bounded multiplicative decrease only after next cooldown; no repeated per-sample shrink |
| pressure | Independent pressure cleared for exit hysteresis | recovering; hold reduced window through recovery dwell |
| recovering | Pressure returns | pressure; shrink on newly verified pressure |
| recovering | Fresh healthy samples persist through recovery dwell and demand exists | normal; resume additive growth |
| recovering | No demand or sensor evidence missing | recovering; hold, no speculative growth |

Saturation `active >= effective_limit` is derived, not a state; warm/hold is an action, not a state. A restrictive window must not self-lock: sustained waiters constitute demand; with independently healthy samples, growth can occur despite no new admissions. Missing sensors inhibit growth but never cause demand-driven shrink. Separate enter/exit thresholds, cooldown and minimum dwell prevent oscillation. Shrink affects only **future** admission, never evicts healthy established connections; positive manual ceiling is never bypassed. Window changes wake permit waiters to re-evaluate.

Hard OS pressure immediately overrides new admission and enters pressure state; recovery uses bounded cooldown and verified fresh samples before reopening. A sampler failure retains the last safe envelope and inhibits growth, or uses finite F at cold startup. Neither demand nor missing samples alone triggers multiplicative decrease or Guardian restart. Rate-limit logs and never spin on repeated accept errors.

## 6. Config/UX contract and migration
The **repository sample and every generated/default pxgo.ini must contain**, under [settings], exactly the equivalent of:
```ini
; Automatic/dynamic connection capacity is recommended. Manual configuration is
; NOT recommended; set max-connections only when diagnosing or mitigating PxGo
; resource or performance problems. A positive value is a HARD CEILING, not a
; target concurrency. 0 disables this manual limit; AUTO remains authoritative.
max-connections = 0
```
Canonical INI key `max-connections` (parser aliases `max_connections` only if the existing canonicalization convention supports it); CLI `--max-connections`, env `PXGO_MAX_CONNECTIONS` with `PX_MAX_CONNECTIONS` legacy prefix precedence consistent with current config. Exact key spelling must be tested across INI/CLI/env and save/merge output; reject negative, overflow and malformed values, including empty typed overrides if current strict policy requires. Default 0. No routine UI slider. Doctor reports mode AUTO, whether manual ceiling is enabled, and provenance without implying manual tuning is recommended.

Legacy `workers` and `threads` remain syntactically **strictly parsed** as integers and round-trip unchanged in existing configs. In active legacy mode, both must be positive and their product must not overflow, preserving current validation and exact connectionBudget behavior. In AUTO, syntactically valid integers are accepted for compatibility but ignored for capacity (including their product); no legacy product/positivity gate is applied to ignored values, though malformed strings remain errors. Explicit nondefault values emit **one startup warning** (not per request), explaining deprecation and no scheduling/capacity effect. Previously invalid malformed historical configs need not become valid. Never map workers*threads to max-connections.

Use **one internal experimental environment selector**, `PXGO_EXPERIMENTAL_CAPACITY_MODE=shadow|auto|legacy`, for staged testing/rollback; not a normal config/INI/CLI tuning key and not exported in generated pxgo.ini. Shadow runs the old gate as sole authority while calculating decisions without acquiring extra permits. Opt-in auto uses the new gate. After Linux/Windows gates pass, AUTO becomes default; retain legacy selector only for one documented rollback window and remove the selector once that window and regression criteria close. Generated INI should omit workers/threads from ordinary tuning instructions or retain them only as commented legacy compatibility examples. Existing config files remain readable; explain changed effective admission after upgrade. Respect existing config precedence `defaults < ini < dotenv < PX_ < PXGO_ < CLI` for supported settings; experimental selector is separate.

## 7. Protocol, auth and overload invariants
- CONNECT: preserve existing handler, upstream establishment, tunnel reservation, buffered bytes, two-way relay, half-close, idle expiry and draining. Downstream admission already covers CONNECT establishment and lifetime; optional single pending-CONNECT counter at handler boundary only if benchmark evidence warrants it, with balanced release on every path. No mandatory separate pending-dial gate or per-transport instrumentation. Existing tunnels are never evicted because the soft window shrinks.
- HTTP: do not conflate downstream sockets, HTTP requests and upstream pooled connections. Keep-alive can serve sequential requests. V1 does not add a universal dial gate or change http.Transport pooling/MaxConnsPerHost; revisit only if measured upstream fanout defeats downstream envelope.
- NTLM/Negotiate: connection-bound authentication remains pinned to its transport/identity; do not close an active authenticated socket or mix credentials to reclaim capacity. Existing per-auth MaxConnsPerHost=1 stays intact; monitor its wait as auth serialization, **not** generic resource overload. Never replay unsafe requests to evade admission.
- WebSocket/HTTP Upgrade, SSE and streaming: preserve exact downstream admission ownership through the full streaming lifecycle; account for upstream resource costs through calibrated safety headroom and existing lifecycle ownership without requiring exact upstream socket counters in V1. Do not apply request-latency AIMD to session duration. No new HTTP latency controller in V1.
- Slowloris: preserve http.Server header/read timeouts on admitted sockets; an accepted-but-waiting socket has its own finite cancellable admission deadline before http.Server owns it. Idle HTTP connections count against admission, with existing IdleTimeout.
- Shutdown: stop new admission, close listeners, drain/close tunnels via existing owner, release leases exactly once; no restart on overload.

## 8. Observability / Doctor
**V1 essential capacity snapshot only:** mode (legacy/shadow/auto), state (normal/pressure/recovering), active_downstream, soft_window, hard_envelope, effective_limit, manual_ceiling_enabled and value when enabled, governing_pressure_reason (or none), aggregate admission_waits and admission_timeouts/rejects, sensor_availability (fresh/stale/unsupported/invalid), last_transition. **Derived, not duplicated:** saturation = active_downstream >= effective_limit; reuse existing top-level ActiveTunnels, Process RSS/goroutines, Runtime and Events; no duplicate active_tunnels or rss_bytes. **Optional/benchmark-only:** p50/p95/p99 admission wait latency, histograms, FD usage, scheduler metrics, pending-CONNECT, exact upstream-open/pending-dial counts. Keep bounded aggregates and redact sensitive identities. Rate-limit event logs; Doctor must explain capacity versus upstream auth/route failures without exposing workers/threads as tuning advice.

**Doctor liveness and security:** `internal/proxy/diagnostic.go` serves `/PxgoDoctor` through the same proxy `http.Server`/listener; a **new** Doctor connection can be unable to enter during saturation (an already admitted connection may still serve it). Do not add a privileged diagnostic listener or bypass capacity/security checks. The controller must run and recover without Doctor requests. Existing local diagnostic events/logging, best-effort fatal snapshots and Process Guardian evidence remain available **where configured/accessible**, not guaranteed always-on out-of-band access. Do not leak capacity state to unauthorized remote clients; preserve existing Doctor request routing/auth/security rules and test them under saturation.

## 9. Test and benchmark acceptance gates (before default switch)
Use existing `docs/benchmarking.md` evidence discipline and `scripts/bench-e2e.sh` with immutable SHA, binary hashes, raw artifacts, manifest, OS/hardware, repeated runs and variance. Baseline old behavior and shadow/new exact builds:
1. Burst HTTP and sustained HTTP at concurrency beyond 32, including 1 KiB/10 MiB, keep-alive, varying upstream delay; success rate, throughput, tail response latency and admission decision p50/p95/p99.
2. Long-lived CONNECT ramps/plateaus above 32 and into pressure, throughput, handshake/accept latency, FD per tunnel, RSS, goroutines and scheduler latency, resource release after disconnect.
3. Forced low nofile/EMFILE, FD/handle exhaustion, memory pressure, cold-start/missing/stale/contradictory sensors and emergency override; verify finite fallback, no busy-loop, deadlock, unbounded socket wait, resource leak or overload-triggered process restart. Include Doctor via a new connection under saturation: it may fail without blocking autonomous recovery; check existing event/fatal evidence and security.
4. AIMD deterministic clock/synthetic samples: demand without pressure must not shrink, healthy sustained waiters can grow despite saturation, noisy threshold, cooldown, stable recovery, missing sensor hold, no oscillation, hard envelope and manual ceiling respected; race Accept/Close, multiple listeners, temporary timeout errors (including capacity release during net/http.Serve retry backoff), shutdown/hijack, backlog fairness and retry amplification; gate-controlled pause before subsequent Accept is the fallback if measured delay/churn is unacceptable, never a separate scheduler.
5. Slowloris/partial headers, read-header deadlines, idle keep-alive, cancel during dial, timeout, proxy fallback, half-close, buffered CONNECT handshake and SSE/WebSocket/Upgrade lifecycle.
6. NTLM/Negotiate and SSPI connection-bound auth (including PAC/WPAD on authorized Windows domain runner), no identity crossover or pooled connection churn; Linux Kerberos where available.
7. Linux **and Windows** release-gating E2E, race/unit tests where supported; macOS additional coverage when practical. Report CPU, peak/current RSS, FD/handles, goroutines, scheduler signal, admission p50/p95/p99, rejects and recovery times.
8. Compatibility matrix for old INI, explicit workers/threads, 0/positive/invalid max-connections, PX_/PXGO_ precedence, --save generated config and Doctor provenance.
No default switch until evidence demonstrates stability, predictable overload, no security/auth regressions, no material baseline regression without explicit approval, and Windows corporate-auth evidence for any corporate-performance claim. Set numeric thresholds **from measured baseline and agreed release criteria**, not unsupported design guesses.

## 10. Rollout and rollback
Phase A instrumentation + shadow controller via the single experimental env selector: existing admission remains authoritative; compare computed window/envelope to real counters; ensure negligible sampler overhead. Phase B selector opt-in AUTO on Linux/Windows with manual ceiling support and selector rollback to legacy admission. Phase C AUTO default only after gates and independent review, retaining selector for a documented rollback window. Phase D remove selector after rollback window and regression criteria close; remove workers/threads from generated normal-user examples while preserving parser compatibility for a documented deprecation window. Shadow must not double-acquire admission or interfere with existing tunnel/transport ownership. Each phase separately gated by exact-head tests and raw evidence. No rollout or implementation is authorized by this document.

## 11. Risks and safe failure
FD estimation may undercount upstream fanout -> reserve calibrated headroom and keep pending-CONNECT measurement optional; memory signals lag -> hysteresis and bounded growth; bounded post-Accept wait reduces burst churn while retaining at most one waiter per listener -> test retry/backlog and timeout backoff; long-lived tunnels occupy capacity -> keep them alive, throttle new work; missing Windows handle data -> conservative fallback + explicit sensor status; unstable sensor sampling -> hold/reduce rather than runaway increase; auth-pinned transport may serialize -> classify separately; legacy config change may surprise operators -> staged rollout and clear Doctor explanation. Process Guardian must not restart on any normal capacity transition.

## 12. Ponytail / YAGNI exclusions and self-review
Explicitly excluded: bespoke epoll/kqueue/IOCP reactor, goroutine pool, workers*threads rebadging, per-route adaptive controllers, ML/PID predictive tuning, latency control for CONNECT/SSE, copying Envoy/HAProxy internals, a second runtime supervisor, automatic process restarts for overload, unconditional fixed 512 cap, aggressive GC tuning, per-connection sampling, global transport MaxConnsPerHost changes.

Self-review (round 1): (a) post-Accept wait is now bounded/cancellable, one per listener, rather than churn-producing immediate close; (b) envelope uses deterministic fresh-sensor min with finite fallback and emergency override; (c) demand only enables growth, independent pressure alone shrinks; (d) AUTO never interprets legacy workers/threads as a ceiling; (e) optional upstream counters and diagnostic histograms are deferred; (f) Doctor saturation is acknowledged without adding a listener; (g) existing auth/tunnel ownership and Guardian fatal boundary remain unchanged; (h) numerical thresholds require benchmark calibration, but decisions/transition rules are specified; (i) no product code, issues or control-plane changes. Remaining independent-audit validation: temporary Accept error integration with net/http.Serve, fairness/backlog tests, and per-platform fallback calibration are **implementation/benchmark gates**, not unresolved architecture choices.
